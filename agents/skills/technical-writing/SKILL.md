# Technical writing

Write for the reader's task. Lead with the problem or result, then provide the explanation or instructions needed to use it. Use real symbols, paths, and commands verified against the current artifact.

Apply **unslop**. Prefer literal wording, clear subjects, and consistent names. Keep the conditions and reasoning the reader needs. Use lists, tables, and headings when they make the information easier to follow.

Read supporting guidance only when needed:

- [Document modes](references/document-modes.md) for choosing the structure of a substantial document.
- [Sentence and procedure guidance](references/sentence-style.md) for dense or ambiguous technical prose.
- [A worked example](references/worked-example.md) when a before-and-after revision would clarify the approach.

For a PR or commit, explain the concrete problem, resulting behavior, and relevant validation. Follow the repository's format. Link detailed evidence rather than pasting logs into the description.

Match code examples to the project's conventions. Follow product copy guidelines for UI strings. Record a recurring writing-rule problem in the shared side-quest list instead of modifying personal skills during an unrelated task.
